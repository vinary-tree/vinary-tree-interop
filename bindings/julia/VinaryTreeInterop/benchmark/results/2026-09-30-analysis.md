# Julia/native boundary measurements — 2026-09-30

This is a measured integration-boundary baseline for
`VinaryTreeInterop.jl`, **not** a comparison of automata algorithms or
end-to-end dictionary throughput. The public ABI fixture is deliberately
tiny: a two-entry byte-key dictionary with optional `UInt64` values, a
two-arc scalar weighted finite-state transducer (WFST), a scalar lattice,
and a dynamic semiring. The benchmark methodology and matched public-ABI
operation definitions are in the [benchmark guide](../README.md); the
[control implementation](../native-control.c) and
[Julia driver](../boundary.jl) are executable specifications.

The qualified baseline is the [committed-harness raw CSV](2026-09-30-threadripper-pro-5975wx-committed.csv)
with its [machine/source manifest](2026-09-30-threadripper-pro-5975wx-committed.csv.meta).
An [independent first full acquisition](2026-09-30-threadripper-pro-5975wx.csv)
and its [manifest](2026-09-30-threadripper-pro-5975wx.csv.meta) are retained
for replication. Both contain eleven alternating native-first/Julia-first
paired blocks per case. The second run records harness commit
`eee469b8442ca28d336f1f6ef36a6b39b96bc7a5` and SHA-256 hashes of
the driver, C control, dictionary fixture, and lattice fixture; the first
was captured immediately before that harness commit with the same timing
code but before SHA-256 metadata was added.

## Acquisition and quality controls

The workstation was an AMD Ryzen Threadripper PRO 5975WX with 64 logical
CPUs. Julia 1.13.1 ran with one thread pinned to logical CPU 8; its
simultaneous-multithreading sibling, CPU 40, was approximately 99–100% idle
in pre-run observations. The Linux `performance` governor was active.
The C control was compiled by GCC 16.2.1 at `-O2`. Each benchmark process
ran under a 3 GiB memory and one-CPU quota, and all build/output files
were on the disk-backed repository filesystem rather than `/tmp`.

Every case completed three untimed warmup rounds. Both full acquisitions
passed independently specified checksums and zero-live-resource checks for
the qualification dictionary, entry cursor, and semiring tokens. Each had
132/132 clean blocks under the predeclared filters. In the committed run,
the maximum recorded load was 7.92 on 64 logical CPUs, maximum Julia
scheduler-wait fraction was 0.00461 against a 0.05 cutoff, and the pinned
core's observed clock range was 4.289–4.292 GHz. No block was removed as
an outlier. The first run's Julia median latency was within approximately
4.5% of the committed run's value in every case; the two runs were not
averaged because only the second has complete source-hash provenance.

## Results

Each time is the median nanoseconds per operation across eleven clean
paired blocks. The Julia allocation column is the median allocated bytes
per operation from a separate short post-warmup run; the native control
does not independently count transient allocations. The ratio is the
median of paired Julia/native block ratios, with a deterministic
2,000-resample percentile-bootstrap interval. These intervals describe
block-to-block variation here, not uncertainty across different machines
or production workloads.

The median per-block resident-set-size delta was zero KiB in every case.
This means the process's resident footprint did not grow measurably across
those short blocks; it **does not** mean the operations allocate no memory.
The Julia allocation column demonstrates transient managed allocations,
and the C fixture performs some native allocations that this runner does
not count separately.

## What the numbers do and do not imply

The control and Julia paths request the same public ABI result, but they
intentionally pay different integration costs. C calls the vtable directly
and releases raw resources; Julia also validates statuses and provider
metadata, constructs typed owned wrappers and finalizers, performs safe
page/graph copies, and translates ABI values into Julia objects. These
checks and ownership guarantees are part of the Julia API contract, not
unexplained automaton work.

The snapshot ratio looks dramatic because the native denominator is only
about 2.84 ns. Julia's absolute median is about 851 ns for an independently
owned, type-checked dictionary wrapper. It would be unsound to conclude
from this ratio alone that native snapshotting is a production bottleneck
or that the architecture should drop ownership checks. Query and WFST
expansion show substantially smaller absolute overheads (about 22 ns and
53 ns respectively) on this fixture.

The largest **absolute** Julia boundary costs here are the two-entry
cursor/page and reducer paths (about 1.78–1.82 microseconds and 1.24–1.36
KiB allocated per operation). A plausible hypothesis is that copying
entry objects and crossing the callback boundary dominate when a page
contains only two entries. That hypothesis requires a page-size sweep with
a representative production provider, plus Julia allocation profiling,
before it becomes an optimization recommendation. The semiring pair/batch
measurements include a fresh operation context on both sides because this
small fixture's token table cannot be reused indefinitely; they do not
isolate the cost of one algebra callback.

The `VALUE_BYTES` dictionary value-domain discriminant is not benchmarked:
ABI v1 lacks byte-value node and entry-page accessors. The missing
versioned capability is tracked in
`vinary-tree-interop-byte-value-dictionary-abi-parity`.
No RC.6 package was published or tagged during this measurement.

For follow-up experiments, first vary page size and dictionary size on
real providers while preserving the same safety semantics; then use
allocation profiling and on-CPU profiles to attribute the dominant cost.
Do not extrapolate these tiny-fixture ratios to whole-application latency
or use them to weaken resource ownership or hostile-provider validation.
